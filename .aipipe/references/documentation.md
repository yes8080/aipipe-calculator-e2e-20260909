# 文档与 GitHub 账本

执行所需的信息必须能从目标仓库和 GitHub 读取。个人笔记、聊天记录和某台机器的绝对路径不能成为开发或验收的前置条件。

## 定稿迁移

初期产品构思可以在 Obsidian 中完成，也可以直接在仓库中开始。方案定稿后，正式方案和必要附件进入目标仓库，经原有 PR 流程形成可访问版本；产品方案放 `docs/` 或项目既有目录，aipipe 自身方案放 `.aipipe/references/`。原稿标记已迁移并冻结，以后需求变更直接修改仓库方案。不要要求开发或验收者读取个人笔记或原聊天。

只要求起草方案时仍可离线完成，不隐含建仓、注册 App 或发布任务。进入正式交付前，设计与发布计划必须在 GitHub 可读取：Issue 引用设计的完整提交 SHA；计划 JSON 是受版本控制的发布输入，开发状态仍以远端任务为准。若设计 PR 尚未合并，可先准备或预览切片；正式开发使用已审查的设计基线。

## 内容放在哪里

| 内容 | 唯一维护位置 |
|---|---|
| aipipe 使用约定、初始化、权限、测试接入、移除指南 | `.aipipe/references/`，随代码通过 PR 更新 |
| 项目接手入口、原生命令、已有设计和任务链接 | `.aipipe/references/project-handoff.md`（项目专用，按需建立） |
| 业务需求、架构、接口与测试设计 | 项目原有文档目录；没有约定时使用根目录 `docs/` |
| 待办、依赖、验收标准、阻塞 | GitHub Issue；形成实施承诺后登记，不只写在笔记里 |
| 批次范围与放行 | GitHub Milestone；只有 Issue 计入进度 |
| 本轮完成项、返修次数、接手提示与待执行操作 | 对应 PR 正文或交接评论；尚无 PR 时写 Issue |
| 独立结论、实际处理人、验收 SHA | 原 PR 的原生 Review；保留退回历史 |
| 测试运行结果 | GitHub Actions / Checks；需要长期复现的用例提交到相应测试目录 |

交接文档是导航与操作说明，不复制一张需要逐轮更新的任务状态表。阅读者从它进入 Issue / PR，回读当前 head、Review、CI、merge 和分支事实。文档与 GitHub 事实不一致时先修文档，不重复初始化、发布或合并。

## 规模与汇总

当前单仓库少量任务使用 Issues 和 Milestone 即可。多模块或跨仓库项目可以用 GitHub Projects 引用既有任务并提供看板/路线图；不复制待办，不要求 Agent 依赖看板才能运行，新增自定义状态需有明确来源，不能与阶段标签分别手动维护。Projects 自动化不在当前 CLI 实现范围，不因此扩大 App 权限。

复杂功能可使用原生父子 Issue 表达层次；实际开发切片才创建开发分支，纯汇总 Issue 不对应 PR，也不与子切片重复计入交付里程碑。当前发布器只处理切片，不自动创建原生父子关系；纯汇总 Issue 不加 aipipe 阶段标签、不混入 released 批次。Discussions 可承载未定范围的讨论，明确任务仍在 Issue；Wiki 不作为正式执行依赖。

## 换工具或机器

1. 克隆目标仓库，读取 `.aipipe/AGENTS.md` 与本轮 Skill；存在项目交接指南时一并读取。
2. 从 `project.json` 核对实际仓库；在 GitHub 读取指定 Issue、关联 PR、当前 SHA、最新交接和未解决 Review。不要求访问原聊天或个人笔记。
3. 本机执行 `aipipe inspect` 和对应角色的 doctor；新宿主只补缺少的角色凭据映射，不把旧宿主凭据可用当作当前可用。
4. 继续原 Issue / 分支 / PR，创建自己的执行身份；必要时请用户手工启动下一工具，提示词包含仓库、Issue/PR、Skill、角色和目标即可。

每次交接在原 Issue/PR 写清：验收或开发的完整 SHA、完成范围、实际测试命令和结果、失败或未执行项、下一步、返修轮次，以及执行身份。合并后回读确认，更新同一记录；文档只在入口、契约或操作方式改变时修改。不要为了写每次进度再创建一个“更新执行清单”的任务。

测试日志有保留期限。长期需要的最小复现须去除 token、私钥、个人路径和临时目录依赖，随修复提交到工具或业务测试目录；PR/Review 引用用例和运行链接。不得以本机临时文件作为唯一验收依据。

## Wiki 与本地笔记

本项目使用仓库 Markdown 作为正式文档：下载或克隆时一起取得，与实现绑定版本并经同一个 PR 评审。GitHub Wiki 是另外的 Git 仓库，需要单独获取，因此不作为必读执行入口；将来需要展示层时可以放导航链接，但不手工维护第二份规范。[GitHub Wiki 文档](https://docs.github.com/en/communities/documenting-your-project-with-wikis/adding-or-editing-wiki-pages)。

Obsidian 等个人知识库只保留链接或明确标记的历史快照，不继续维护进度与启动指令。aipipe 专属文档保留在 `.aipipe/`，卸载时随工具移除；业务设计保留在产品目录，GitHub Issue/PR 的历史不随卸载删除。

## 同轮同步约定

每次发布 aipipe 资源或 CLI 新版本，同步模板、当前验证项目、全局安装入口与生成的运行文件，核对版本和有效测试。保留项目配置、原计划、业务代码、测试、定制入口和工作流；提交推送后才报告已同步，主分支仍按原独立验收与 CI 门禁合并。

## 通用资源与项目实例

正式 aipipe 文档、Skills、模板和安装资源只包含通用约定、匿名示例及工具自身的版本证据。下游项目名称、URL、真实 App/Installation ID、业务进度和实测流水账保存在各自项目的 GitHub 中，不复制到工具规范。维护环境的验证项目清单不硬编码进分发资源；同轮同步要求继续有效。

维护设计草稿保存在 `.aipipe/drafts/`，不进入安装包或 scaffold。定稿后更新对应正式主题；草稿不得宣称提议命令已经可用。
