# 初始化验收方法

本指南规定可复用的验证步骤和证据边界。真实仓库、App/Installation ID、个人路径和业务执行记录保留在运行验证的项目中，不作为 aipipe 安装资源分发。

## 分层验收

| 层次 | 验证内容 | 证据归属 |
|---|---|---|
| 配置与工具行为 | 参数校验、预览不写入、已有资源复用、回调 state、凭据保存、分页、恢复与安装入口 | 工具仓库匿名行为测试及 CI |
| GitHub 接口集成 | 已授权仓库与 App 的真实创建/安装、角色鉴权、规则生效、写入与合并回读 | 执行验证的项目 Issue/PR/Review/Checks |
| 独立业务验收 | 两个独立上下文、有效业务测试、当前 SHA 原生审批、必需 CI、main 回归与分支清理 | 业务项目的原 PR 和 CI |

单执行者切换两套 token 只能证明平台接受不同账号，不能冒充两个独立 AI 上下文。工具单测通过不等于初始化完整或业务验收完成。

## 验证顺序

1. 使用获授权的隔离仓库，先明确资源与权限范围。只创建缺少的对象，复用已验证的 App；不为重跑测试重复注册。
2. 用 gh 创建或绑定仓库，回读真实 default branch 和合并设置。初始化部分完成必须逐项报告，不能仅凭 repository/default_branch 宣称可交接。
3. 验证 manifest 一次性回调和 conversion；私钥直接保存到仓库外，错误 state 不接受、不输出秘密。回调结束后关闭监听。
4. 分别验证 App 安装范围、单仓库 token、真实 bot 身份与到期时间；POSIX 文件权限为 0600。新宿主须重新检查本角色凭据，不能假设自动继承。
5. 先准备业务 CI 契约，再核验实际检查来源和规则。原有保护不自动降级，两个角色不获取 Workflows 或 Administration 写权限。
6. 验证 Developer 可提交 PR 但不能自批或合并，Delivery 可独立批准但不能写受限开发分支；拒绝结果记录 HTTP 与资源，不能仅凭一次 404 推断不存在。
7. 使用当前 SHA 的普通合并路径，回读 merged、合并 SHA、Issue 状态、main 检查和分支删除。发起 auto-merge 成功不能替代这些事实。
8. 保存脱敏最小复现到通用测试目录；实例日志、具体资源 ID、运行链接和验收报告保存到原项目。撤销仅为测试创建的临时对象须有明确范围，保留共享资源。

## 已固化的接口约定

- GitHub App 注册使用 manifest 与 conversion；不要假设存在普通 `gh app create` 命令。
- manifest 的 hook 配置必须完整；关闭 Webhook 不意味着可以省略所需 URL。
- App JWT 请求使用 Bearer 认证；installation token 按 gh 的 token 方式注入，不能在诊断中泄露认证头。
- 浏览器安装时核对选择的仓库；随后用 API 回读实际安装和 token 可见范围。
- 某类用户 token 不能枚举安装时，先检查对应鉴权接口，不据此重复注册 App。
- 短期 token 过期由受信 Owner 环境重新签发；普通角色操作不读取私钥。同一系统账号的文件权限不构成 Agent 进程隔离。
- 合并成功后的 metadata 失败只恢复 metadata，不重复成功的 Review/merge。

## 报告要求与未覆盖场景

报告必须写清验证版本、提交 SHA、命令、结果、实际执行身份以及未执行项。模拟回归与真实接口证据分别标注，不把浏览器路径的局部验证描述为完整端到端注册。

组织 SSO/安装审批、无浏览器远程初始化、Windows、密钥轮换与丢失恢复需专门环境。未做真实验证就保持未验证状态，不根据通用设计推断已经支持全部平台。
